# Правила разработки по Simple Architecture

Этот документ переводит идеи из конспекта
[`1.first-steps.md`](../lecture-notes/1.first-steps.md) в практические инструкции
для AI-агентов, работающих над проектом.

## Цель архитектуры

Архитектура должна уменьшать человеческие трудозатраты на создание, изменение
и сопровождение приложения. Предпочитай решение, которое:

- легко найти в файловом дереве;
- легко прочитать без изучения большого файла;
- можно изменить локально, не затрагивая несвязанные части приложения;
- позволяет добавлять функции без переписывания существующего кода целиком.

Не усложняй структуру ради абстракции. Новая папка, функция или хук должны
отделять самостоятельную ответственность либо обозначать понятную часть UI.

## Основное разделение: View и Presenter

Каждый React-компонент считается View-слоем.

View-файл должен:

- импортировать дочерние компоненты, CSS Module и `usePresenter`;
- один раз вызвать `usePresenter`;
- получить готовые к отображению данные и обработчики;
- вернуть JSX, описывающий интерфейс.

Сохраняй результат `usePresenter` в переменную `presenter`. Не сокращай её до
одной буквы: имя должно передавать роль объекта и оставаться понятным в JSX.

Во View запрещено размещать прикладную JS/TS-логику:

- запросы к API;
- `useState`, `useEffect` и другие управляющие хуки;
- фильтрацию, сортировку и преобразование данных;
- валидацию;
- подготовку отображаемых значений;
- сложные обработчики событий.

Эта логика должна находиться в `usePresenter.ts`. Presenter отвечает за
состояние, запросы, производные данные, сценарии взаимодействия и функции,
которые View привязывает к элементам интерфейса.

Пример границы:

```tsx
// SearchForm/index.tsx — View
import styles from './styles.module.css'
import { usePresenter } from './usePresenter'

export function SearchForm() {
  const { query, onQueryChange, onSubmit } = usePresenter()

  return (
    <form className={styles.form} onSubmit={onSubmit}>
      <input value={query} onChange={onQueryChange} />
    </form>
  )
}
```

Если `usePresenter.ts` становится большим, не переноси логику обратно во View.
Раздели Presenter на небольшие локальные хуки и чистые функции.

## Расположение типов компонента

Размещай тип рядом с кодом, который непосредственно его использует:

- типы, используемые только Presenter, объявляй в `usePresenter.ts`;
- типы, используемые только View, объявляй в `index.tsx`;
- типы, используемые несколькими файлами компонента,
  выноси в локальный `types.ts`;
- общие предметные типы нескольких компонентов размещай в `types.ts` у их
  ближайшего общего владельца.

Не складывай в `usePresenter.ts` типы только потому, что они относятся к тому
же компоненту. Presenter должен содержать лишь те типы, которые нужны его
сигнатуре или реализации.

Если Presenter принимает props компонента, тип экспортируй из
`usePresenter.ts` под именем `Props`, а во View импортируй через `import type`:

```tsx
import { usePresenter } from './usePresenter'
import type { Props } from './usePresenter'

export function ShowItem(props: Props) {
  const presenter = usePresenter(props)

  return (
    <button type="button">
      {presenter.label}
    </button>
  )
}
```

Если Presenter не использует props или другой View-тип, не переноси этот тип в
`usePresenter.ts`: оставь его в `index.tsx`.

## Структура папки компонента

Для каждого нового компонента создавай отдельную папку:

```text
ComponentName/
├── index.tsx
├── styles.module.css
├── usePresenter.ts
├── hooks/               # только для выделенных сценариев Presenter
└── validation.ts        # только если компоненту нужна валидация
```

Правила именования:

- папка компонента называется в `PascalCase` и хранит его имя;
- называй компонент по его смыслу, данным или роли в интерфейсе, а не по
  текущему визуальному оформлению;
- предпочитай устойчивые названия вроде `Header`, `Footer`, `SearchForm`,
  `ResultsControls`, `ShowsList`, `ShowItem` и `ShowDetails`;
- не используй визуальные метафоры вроде `Room`, `Sign`, `Shelf`, `Cassette`
  или `Television`, если они описывают только текущий дизайн;
- основной View-файл каждого компонента всегда называется `index.tsx`;
- импортируй компонент по пути к папке, не добавляя `/index` в import;
- не создавай рядом с `index.tsx` дублирующий файл `ComponentName.tsx`;
- Presenter всегда называется `usePresenter.ts`;
- стили компонента находятся в `styles.module.css`;
- используй CSS Modules без CSS-препроцессоров;
- записывай пользовательские тексты в JSX и Presenter обычным регистром; если
  по дизайну текст должен отображаться заглавными буквами, используй в CSS
  `text-transform: uppercase`, а не текст в верхнем регистре в исходном коде;
- храни все брейкпоинты ширины экрана в `src/styles/media.css` как
  `@custom-media` и используй в CSS Modules их имена; не дублируй числовые
  значения ширины в локальных `@media`;
- не используй `var(--breakpoint)` в условиях `@media`: CSS custom properties
  там не поддерживаются; общие custom media разворачиваются PostCSS во время
  сборки;
- в CSS Modules допускай не более одного уровня вложенности селектора:
  `.room-pages button` разрешён, а `.room-pages button span` запрещён;
- ограничение вложенности не распространяется на глобальные стили; если без
  более глубокого селектора в CSS Module нельзя обойтись, не отключай Stylelint
  самостоятельно, а сначала запроси явное разрешение пользователя;
- не записывай CSS в сжатом виде: селекторы и декларации должны быть
  отформатированы Prettier;
- давай вынесенным хукам и функциям предметные имена;
- не создавай пустые `components`, `hooks` и другие папки заранее.

Не используй папку `components` как обязательный промежуточный уровень для
всех дочерних View. Компонент, используемый только владельцем, размещай прямым
потомком его папки: `ResultsSection/ShowsList/ShowItem`, а не
`ResultsSection/components/ShowsList/components/ShowItem`. Создавай
`components` только для View, которое уже используют несколько частей одной
ветки; папка `src/components` предназначена для компонентов, используемых в
независимых ветках приложения.

После создания или изменения стилей запускай `npm run format:styles`. Команда
`npm run lint` включает `npm run format:styles:check` и должна завершаться без
ошибок. Не отключай и не обходи проверку форматирования для отдельных
CSS-файлов.

JSX во View оформляй развёрнуто:

- после `return (` всегда начинай JSX с новой строки, а закрывающую `)` размещай
  на отдельной строке;
- каждый JSX-тег и JSX-элемент размещай на своей строке;
- не записывай вложенные элементы в одну строку, например
  `<div><span>Текст</span></div>`;
- содержимое элемента размещай между открывающим и закрывающим тегами на
  отдельных строках;
- многострочный JSX в условиях, стрелочных функциях и свойствах также заключай
  в круглые скобки с переносами строк.

Соблюдение этого формата проверяют JSX-правила ESLint. После изменения TSX
запускай `npm run lint` и не отключай правила локальными комментариями.

Максимальная длина строки в TypeScript, TSX и комментариях — 120 символов.
Переноси длинные выражения, аргументы, свойства и JSX-атрибуты на несколько
строк. Ограничение проверяет ESLint, а `printWidth` Prettier также равен 120.

React-код проверяется современным preset
`@eslint-react/eslint-plugin/recommended-typescript`. Вместе с ним используются
официальные рекомендуемые правила ESLint, TypeScript ESLint, React Hooks и React
Refresh. Проектные соглашения по форматированию дополняют эти presets.

В объектных литералах каждое свойство размещай на отдельной строке, включая
объекты с единственным свойством и объекты внутри массивов. Открывающую и
закрывающую фигурные скобки также размещай на отдельных строках. Соблюдение
правила проверяет ESLint.

Правило `index.tsx` обязательно для компонентов, расположенных в собственных
папках. Корневой компонент приложения остаётся в `src/App.tsx`: не создавай для
него отдельную папку `App`. Файл `main.tsx` является точкой запуска приложения,
а не View-компонентом, поэтому также сохраняет своё имя.

## Древовидная архитектура

Файловая структура должна повторять структуру интерфейса. Дочерний компонент
располагай внутри папки того компонента, частью которого он является:

```text
ShowsExplorer/
├── index.tsx
├── styles.module.css
├── usePresenter.ts
├── SearchForm/
│   ├── index.tsx
│   ├── styles.module.css
│   └── usePresenter.ts
└── ShowsList/
    ├── index.tsx
    ├── styles.module.css
    ├── usePresenter.ts
    └── ShowCard/
        ├── index.tsx
        ├── styles.module.css
        └── usePresenter.ts
```

По пути к файлу должно быть понятно, где этот элемент находится в UI. Не
складывай все компоненты, хуки или функции проекта в одну глобальную папку.

Соблюдай границы дерева:

- родитель может импортировать свои дочерние компоненты;
- локальный компонент не должен импортироваться из несвязанной ветки;
- не импортируй внутренние файлы другого компонента напрямую;
- взаимодействие с дочерним View выполняй через его публичные props;
- вспомогательную логику держи рядом с самым верхним узлом, которому она нужна.

## Когда компонент становится переиспользуемым

Выбирай область размещения по фактическому использованию, а не по возможному
переиспользованию в будущем:

1. Используется только одним компонентом — храни прямым потомком его папки.
2. Используется несколькими компонентами одной ветки — подними в папку
   `components` их ближайшего общего родителя.
3. Используется в разных независимых ветках приложения — помести в
   `src/components`.

Не переноси компонент в `src/components` после первого появления. Глобальная
папка предназначена только для действительно общих компонентов.

## Размер и декомпозиция файлов

Ориентир — не более 120 строк в одном файле TypeScript или TSX. При приближении
к этому размеру сначала проверь, не смешаны ли несколько ответственностей.

Разделяй код осмысленно:

- самостоятельную часть интерфейса выноси в дочерний компонент;
- самостоятельный сценарий или состояние — в отдельный хук;
- вычисление без React — в чистую функцию;
- валидацию — в отдельную локальную функцию или файл;
- повторяющуюся логику — в хук на ближайшем общем уровне дерева.

Не выполняй обходы больших списков на каждом рендере Presenter. Данные, не
зависящие от состояния интерфейса — например, уникальные жанры поисковой
выдачи — вычисляй один раз при преобразовании ответа API. Производные данные,
зависящие от состояния интерфейса, вычисляй через `useMemo` или чистую функцию,
переданную в `useMemo`. Если для одной выдачи нужны и количество, и элементы
страницы, предпочитай один проход по списку нескольким последовательным
`filter`, `slice`, `find` и другим обходам.

Не дели связанную логику на искусственные фрагменты только ради количества
строк. Цель ограничения — читаемость и простота изменений.

## Запросы и TanStack Query

View не должен знать, как выполняется запрос. Хуки TanStack Query вызываются в
Presenter либо в небольшом специализированном хуке, который использует
Presenter.

Presenter должен вернуть View уже подготовленное состояние интерфейса:

- данные для отображения;
- признаки загрузки, ошибки и пустого результата;
- обработчики повтора запроса и пользовательских действий;
- отфильтрованные и разбитые на страницы элементы, если это локальная логика.

## Алгоритм работы AI-агента

Перед реализацией изменения:

1. Определи место новой функции в дереве интерфейса.
2. Найди ближайший компонент-владелец.
3. Реши, достаточно ли изменить его Presenter или нужна отдельная ветка UI.
4. Размести новые файлы в самой узкой подходящей области.
5. Не создавай глобальную абстракцию без существующего повторного использования.

Во время реализации:

1. Сохраняй View декларативным и свободным от прикладной логики.
2. Формируй данные и обработчики в Presenter.
3. Используй локальный CSS Module.
4. Форматируй CSS командой `npm run format:styles`.
5. Разделяй крупные Presenter-файлы по ответственностям.
6. Не нарушай границы соседних веток дерева.

После реализации проверь:

- можно ли понять положение компонента в UI по пути к его файлу;
- останется ли название компонента верным после смены визуального дизайна;
- называется ли основной View-файл компонента `index.tsx`;
- расположен ли каждый тип рядом с кодом, который непосредственно его
  использует, и нет ли во `usePresenter.ts` типов только для View;
- остались ли во View запросы, состояние, преобразования или валидация;
- не оказался ли локальный компонент в глобальной папке;
- нет ли файла, который стал трудно читать или приблизился к 120 строкам;
- проходят ли `npm run lint` и `npm run build`.
